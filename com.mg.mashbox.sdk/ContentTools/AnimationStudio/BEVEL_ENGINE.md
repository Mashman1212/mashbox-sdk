# Bevel engine: straight-skeleton integration

## Decision and current implementation

The user's target is a reusable, performant bevel whose straight chamfers preserve parallel rails and planar faces, including successive independent bevel operations. Avoid accumulating shape-specific corner corrections. Use established moving-line geometry, explicit topology identities and collision events.

Straight-skeleton wavefront integration (2026-10-22): the user rejected further local endpoint patches and explicitly requested an established bevel foundation. Editor/StudioMeshCuts.BevelWavefront.cs now uses the MIT-licensed Briganti Unity straight-skeleton wavefront kernel, vendored under Editor/ThirdParty/BrigantiStraightSkeleton at upstream commit 2d26dc6fe1ff1f08f12305625ab54fd46e12d1ea. Local extensions support weighted and stationary boundaries. Selected edges move as parallel face-plane lines; unselected boundaries remain stationary. Corners follow intersections of those moving lines. Distinct face-plane cuts on a shared edge retain separate identities, with matching subdivisions inserted along retained edge spans before the existing strip/corner stitching. A single-segment chamfer now uses its geometric flat normal rather than curved-profile endpoint normals.

The immutable source/selection caches trajectories and the earliest edge-collapse or reflex split event. Width edits evaluate this cached plan; topology/selection changes reconstruct it. Fractional width normalization uses the smallest local edge budget per connected selected region, multiplied by 0.45, with exact linked-edge miter speed ratios as described below; the public Width range/default is unchanged. All selected regions share the earliest normalized collision limit. The old repeated half-width draft retries and bisection fallback are removed. Atomic inset validation remains; an unsafe profile/junction reports an error instead of silently substituting a smaller shape. Planar source faces use their own charts; incident non-planar polygons now use local authored-triangle charts as detailed under Imported frame bevel and component-drag correction. Face coordinates are normalized to approximately 0..100 for upstream floating-point predicates.

Scope is deliberately precise: this replaces offset construction and collision limiting with an actual straight-skeleton wavefront interval. It clamps immediately before the first event. It does not advance the 3D mesh through collapse/split events or implement automatic post-collision topology merging. Existing profile interpolation, Grid/Cap junction generation, attribute transfer and publication remain. It is not a global 3D straight-skeleton solver or global self-intersection solver. Rounded high-valence junction construction is still the existing implementation. Local-space fractional distances remain local-space; no new world-space/absolute width option was added. Do not describe the entire bevel engine as a complete Maya-equivalent replacement. See BEVEL_ENGINE.md for the architectural analysis and remaining work.

## Why straight skeleton, rather than medial axis

Straight-skeleton fronts are offset supporting lines. Adjacent fronts meet along angle bisectors (weighted bisectors for unequal speeds). The medial axis instead measures distance to finite boundary features. For convex polygons these constructions coincide; they differ at reflex features. A medial axis is not required to define the desired linear chamfer rails. CGAL documents these distinctions and the edge-collapse/reflex collision events: https://doc.cgal.org/latest/Straight_skeleton_2/index.html .

A per-face 2D skeleton is insufficient by itself for a selected-edge bevel on a 3D mesh. Adjacent face charts must agree on shared boundary subdivision, source vertex ownership and junction connectivity. Running a whole-solid 3D skeleton is a separate problem: general nonconvex polyhedra have ambiguity and substantially different complexity. Reference: https://arxiv.org/abs/0805.0022 .

Maya's public bevel node documentation exposes parallel-edge, offset/fraction and miter controls, but does not establish its private implementation: https://help.autodesk.com/cloudhelp/2024/ENU/Maya-Tech-Docs/Nodes/polyBevel3.html . Blender's public BMesh implementation demonstrates separate offset intersections, vertex-fan boundary construction, width adjustment, collision limiting and profile/junction construction. These support the architectural separation; its GPL code was not copied: https://github.com/blender/blender/blob/main/source/blender/bmesh/tools/bmesh_bevel.cc .

## Reused implementation and local extensions

Source: https://github.com/Briganti-Games/Straight-Skeleton-Generator . MIT copyright and permission notice are retained alongside the vendored files. Only the wavefront geometry dependencies are included, under an isolated Editor namespace. The source is compiled directly into the Studio Editor assembly; no new runtime assembly or per-frame service is created. Unity.Mathematics 1.3.3 is now an explicit SDK package dependency and Editor assembly reference.

The upstream kernel supplies graph construction and collision-event analysis. Studio adds per-boundary speeds, including zero for unselected boundaries. Corner velocity solves the two moving-line constraints `n0 dot v = speed0` and `n1 dot v = speed1`. With equal unit speeds this recovers the unweighted angle bisector. Relative corner motion handles collapse into stationary corners. Reflex-to-edge timing uses the target edge's speed. These extensions are documented in ThirdParty/BrigantiStraightSkeleton/UPSTREAM.md.

The integration consumes the initial event interval and caches resulting 3D trajectories. It does not construct a complete skeleton graph to extinction. Floating-point positions/predicates remain; this is not an exact-arithmetic kernel. Normalizing each face chart reduces dependency on mesh units. Degenerate or incompatible parallel constraints produce an explicit failure instead of an arbitrary displacement.

## Evaluation pipeline

1. Capture immutable editable polygon topology and geometric adjacency. Keep render triangulation separate.
2. Assign fractional offset budgets consistently within each connected selected-edge region.
3. Build planar face charts and weighted wavefront graphs. Cache corner velocities and the earliest event.
4. Clamp the requested normalized width before that event; evaluate positions from the captured source.
5. Preserve distinct intersections belonging to different incident faces. Subdivide retained boundary spans at every shared cut to avoid T junctions.
6. Reuse strip/profile and corner-junction generation, interpolate source attributes, then atomically validate and publish through the existing MeshData preview path.

Width drags do not recompute graphs. The shared one-shot EditorApplication.update scheduler, source restoration, bounded grouped Undo, pane shortcut shield and post-commit bevel selection clearing remain in place.

## Remaining engineering work

- Continue through skeleton collapse/split events using an atomic 3D topology transaction, including simultaneous events and source/UV provenance. Merely welding nearby points is insufficient. Current behavior is collision clamping.
- Replace or formally constrain the existing rounded high-valence junction construction if the required shape differs; skeleton offsetting alone does not specify a fillet patch.
- Incident non-planar polygons now use local authored-triangle charts without flattening unrelated geometry; verify more concave/production surfaces before claiming unrestricted non-planar support.
- Extend geometric coverage to representative concave production meshes and very small/large features before claiming broad robustness.
- Verify actual Studio shading and interaction. CPU planarity/manifold checks and the isolated timing measurement do not establish rendered appearance or interactive FPS.

These items are part of the user's requested bevel foundation, not a claim that the full architecture has already shipped. Preserve truthful status in STUDIO_HANDOFF.md.

The derived charts are cached with the captured source/selection and publish only with the bevel result. Committing such a bevel can create explicit triangle boundaries on the affected warped faces; cancellation restores the source polygons. This is a defined faceted-surface treatment, not a general smooth non-planar skeleton.
- Publication preserves untouched source faces, authored triangle diagonals and exact source vertex attributes, including retained normals/tangents. Only changed/generated faces are triangulated. No unrelated source-geometry cleanup is performed. Source triangle membership is cached per captured topology. Missing authored normals receive area-weighted fallback normals.
- Ear convexity, point-in-triangle and final-triangle validity now use a filtered orient2d predicate: a double determinant/error bound, followed by exact BigInteger arithmetic on binary32 coordinates when ambiguous. Geometric offset tolerances no longer classify tiny valid triangulation ears as degenerate. This follows the filtered-exact predicate approach described by Shewchuk (https://www.cs.cmu.edu/~quake/robust.html); it does not make the whole bevel kernel exact arithmetic. True degenerate/new invalid faces still fail atomically.
- Component Move/Rotate/Scale gestures retain statistics caches while dragging, then invalidate them at MouseUp or the next idle-handle SceneGUI event. Geometry, normals, tangents and overlays continue updating with every edit. Ordinary non-gesture position edits invalidate immediately. Recalculation now reads stored polygon boundaries directly, rather than building a StudioMeshCuts neighbour graph just to count. On the Body probe the old count rebuild averaged about 56 ms; corrected samples were about 2.7–4.3 ms, and that rebuild is absent from continuous drag samples. Counts can temporarily retain the pre-drag welded totals if points coincide/separate during a gesture; they refresh on completion. No timer, frame cap, hover throttling or idle repaint loop was added.

### Dense-mesh live bevel and GPU publication (2026-10-23)

The user confirmed Width dragging, rather than opening the pane, was slow. Selection stutter was on marquee release; indexed/batched visibility remains as described below. Performance is a requirement for every live sample, with no throttling or release-only preview.

- The captured straight-skeleton plan owns immutable source positions, selected/affected/static face lists and weighted trajectories. Width edits retain source prefixes and construct only the affected neighborhood. Static polygons no longer enter per-sample corner-fan/stitching loops.
- Publication assigns stable render slots to dynamic polygon corners. Hashing evaluated normal/UV floats previously alternated the frame's vertex count and invalidated whole-mesh wire/face/statistics caches in 13 of 50 warmed samples. The corrected test has zero topology changes. Geometric identities and smoothing groups preserve editable seams; untouched source polygons, triangles, materials and attributes are retained.
- Only dynamic positions, normals, colors, tangents and UVs are packed into a reusable stream-update packet. Working and live CPU meshes receive the same suffix. Bounds combine a cached static bound with the dynamic patch. Native Unity tangent calculation runs on the disconnected dynamic render corners. Missing source tangents are generated for the retained prefix once, rather than falling back to a whole-mesh recalculation on every sample. Canonical attributes and native tangent results are checked independently.
- Renderer MeshFilters temporarily use one GPU-only render mirror per touched mesh, shared by its instances. Its CPU vertex data stays unchanged during stable drags; direct GraphicsBuffer.SetData range writes update only changed GPU attributes. CPU Work/Live meshes remain current for editing, visibility/picking, metadata, saving and Undo. Source/render topology changes rebuild the mirror once. Reset, zero width, commit, cancel, Undo and disposal restore the authoritative MeshFilter bindings and release owned buffers/meshes. Unsupported GPU access falls back to the current CPU-published mesh. No compute shader is required for these already-computed sparse updates. The design follows Unity's GPU-buffer API: https://docs.unity3d.com/ScriptReference/Mesh.GetVertexBuffer.html and https://docs.unity3d.com/ScriptReference/GraphicsBuffer.SetData.html .
- Querying vertexBufferCount on dirty working/live meshes forced source-sized native GPU preparation, including the off-scene work copy. Stable packets validate vertex descriptors without that getter. The render mirror prevents deferring that same full upload into drawing: the million-vertex rendered regression dropped native draw preparation/submission from about 7 ms to about 0.007 ms, with changed GPU attributes verified by readback.
- Selection remapping uses a cached render-edge index and generated edge IDs. Live welded membership uses static/dynamic geometric links. Handle centers/statistics reuse published positions, and Local orientation uses incident-face adjacency. Ordinary polygon wireframes use their existing GPU position buffer with suffix uploads; unused duplicate whole-mesh CPU line geometry is not built. These remove source-sized scans/uploads from stable Width edits.

### Sequential bevel miter agreement and integer scrubbing (2026-10-23)

The reported surface was closed, with an extra thin face/doubled edge. Reproducing the first chamfer followed by its three-edge border gave fifteen geometric vertices/eleven faces, including an artificial corner triangle. An installed Blender operator reference produced fourteen vertices/ten faces; its exact positions differ because of its width/loop-slide policy. No GPL implementation was copied.

At a manifold three-face corner with exactly two selected edges, their outer face offsets must reach the same point on the stationary edge. For face angle theta, travel is offset/sin(theta). The engine solves those exact offset ratios over linked selected edges before building weighted straight-skeleton face trajectories, normalizing the largest edge speed to the existing region budget. Each selected edge keeps one constant speed at both endpoints: rails remain parallel, source supporting planes remain fixed, and the corner shares one geometric point without a filler sliver. Inconsistent ratio cycles keep their separate fans; this is not a global high-valence miter solution or post-event collapse merger. Width normalization is still fractional local space, with an upper region budget based on 45% of the smallest incident edge. The reproduced case now has fourteen vertices/ten faces with planar faces at second widths .074, .449 and 1. No final-mesh proximity welding or thin-face deletion was introduced.

ToolChannelPane integer label scrubs now accumulate unscaled logical pointer movement at twelve pixels per step at 1x, independent of the starting integer or Unity's native integer acceleration. The shared 0.1x/1x/2x/4x multiplier applies linearly. Fractional motion accumulates; bounds discard overshoot, reversing responds immediately, Escape restores the captured start, and focus loss/Undo/disposal release capture. Numeric text entry remains native. Floating fields retain their existing precision path. Validation passed 64 accumulation/rate/clamp checks and 12 native label-scrub checks.
